## 8. Jev-coordinated application preparation

[PLAN-019](plans/PLAN-019-application-preparation-framework.md), [PLAN-021](plans/PLAN-021-evidence-led-generation-quality.md), and accepted [ADR 0023](decisions/0023-application-preparation-and-action-boundaries.md), [ADR 0024](decisions/0024-model-aware-token-budgeting.md), [ADR 0025](decisions/0025-jev-approval-of-tailored-resume.md), [ADR 0026](decisions/0026-jev-categorical-evidence-support.md), [ADR 0027](decisions/0027-explainable-jev-resume-review.md), and [ADR 0035](decisions/0035-application-heading-and-two-evidence-paragraphs.md), [ADR 0036](decisions/0036-specific-project-evidence-and-direct-role-links.md) record the implemented local flow and remaining enablement work. Jev remains the sole matching validator. After a single-listing **Prepare application** click, the local Clue harness passes its read-only, versioned result to GPT-6 Luna (`gpt-6-luna`, `reasoning.effort=high`) through the OpenAI Responses API. A separate Researcher directs bounded public contact research through the existing Scrapling crawler; the Diagnoser, Recruiter, and Rewriter generate evidence-grounded CV, cover-letter, answer, and outreach drafts. The Researcher receives no candidate profile; Diagnoser receives the selected CV plus job/Jev context; Recruiter receives exact mapped technical-profile evidence; Rewriter receives only profile excerpts mapped by Recruiter plus selected descriptive/style references. Before generation, Clue counts each stage request with OpenAI's token-count endpoint, checks the current model context window, and reserves local spend from the exact input count and configured output allowance. Optional Hiring Manager practice gets technical-profile context after its own action. Jev checks each generated factual block against the exact cited excerpt, then separately must explicitly approve the final tailored resume against the saved job. That final decision cannot mutate the original match, and its uncalibrated confidence is diagnostic only. A reviewable packet requires exactly two distinct Jev-supported, role-sourced project-evidence paragraphs; the local application heading supplies intent, and failures produce no documents. The renderer adds a CV-derived contact header when present, date, application title, salutation, polite close, and name. Unknown or AI-assisted descriptive profiles are style guidance only. The owner may select a base CV and preserve or improve its structure. Clue validates and renders versioned drafts locally; the owner reviews the complete packet once before any external action.

The implemented flow includes reviewed evidence, a durable queue, Jev-to-GPT snapshot handoff, structured stage outputs/tool allowlists, local rendering, separate API usage accounting and consent, bounded public contact research, suppression, owner feedback, and an exact-approval Gmail draft adapter. Jev checks generated blocks against approved claims, exact technical-profile excerpts, and verified public evidence. Unknown or AI-assisted descriptive profiles guide style only. Technical-profile entailment does not verify the source's truth. The repository template keeps `OPENAI_API_KEY=` empty; the owner's local key and consent remain in private local configuration. M8 renders the local application heading and two evidence paragraphs. Prompt `.38` now passes live IFOM testing: the v13 gate and both Jev paragraph checks passed, Jev separately approved the CV, and Word/Poppler inspection found no clipping. The two body examples follow the owner's compact direct-action reference. No CV edits or outreach draft were produced despite one sourced inbox. No email or application action occurred. See PLAN-020, ADR 0030–0037, and the current [evaluation report](evaluations/PLAN-020-evaluation-results.md). Applications and sent outreach remain manual; the GPT agent has no Gmail or send tool. Automated reminders, external tracker sync, cohort analytics, and an optional worker remain deferred.

Search discovery, deduplication, deterministic hard filters, and Jev matching remain automatic. Mined or selected listings do not start research or generation. A scored listing with verified location eligibility waits for the owner to click its specific **Prepare application** card action when Jev says `match`, or **Prepare for review** when Jev says `review`; the dossier preserves that state and shows unresolved checks. Conflict, unassessed, and unverified/ineligible location results remain blocked. The individual click triggers the full bounded research and document packet for that job and reserves its OpenAI budget. No bulk or scheduled start is allowed. Mock interview practice is a separate optional trigger for that listing. M2's generated flow uses a separate GPT-6 Luna Researcher role (the only stage with bounded public-crawl tools), followed by Diagnoser, Recruiter, Rewriter, and optional Hiring Manager practice calls at `reasoning.effort=high`. The Diagnoser reports visible extraction/layout risks, not exact ATS outcomes; the Recruiter maps job criteria to evidence while Jev remains the only fit validator; the Rewriter applies the Google XYZ pattern only to verified facts and metrics; interview ratings remain practice feedback. A separate Jev support check assesses each generated block only against linked approved evidence, verified public sources, saved job facts, or a narrowly scoped owner preference source for a cover-letter preference; unsupported and unresolved blocks are omitted before rendering, and this check cannot alter matching. See PLAN-019 and ADR 0023/0028 for workflow contracts and PLAN-020 for evaluation status.
