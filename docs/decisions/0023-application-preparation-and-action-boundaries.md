# ADR 0023 — Jev-coordinated application preparation and human action boundary

- Status: Accepted — core M0–M5 local implementation recorded; API enablement and optional follow-ons remain gated/deferred
- Date: 2026-10-06
- Related: [PLAN-019](../plans/PLAN-019-application-preparation-framework.md), [ADR 0006](0006-jev-scoring-and-budget-guard.md), [ADR 0016](0016-durable-applied-tracker.md)

## Context

Clue discovers and ranks jobs with the existing Jev integration. Its product definition keeps application decisions and submission on the employer's site, and its applied tracker distinguishes owner attestation from receipt evidence. The owner approved a local preparation framework that uses Jev together with an OpenAI API agent. Core local workflow code is now implemented; provider calls remain disabled until separately configured.

Jev is the matching validator. GPT-6 Luna (`gpt-6-luna`, `reasoning.effort=max`) directs bounded public research and prepares tailored CVs, cover letters, application answers, and outreach drafts. It uses the existing Scrapling-backed Clue crawler, the technical profile as a reviewed evidence source, the descriptive profile for confirmed writing preferences, and owner-selected CVs for content/layout. The owner can set a default CV or let the agent recommend/select from permitted references and can choose whether to preserve or improve their structure. Clue's ordinary code owns hard gates, state, source/claim validation, budgets, permissions, and local rendering. The owner reviews the complete packet at one final checkpoint, manually submits applications, and manually sends outreach.

## Decision

1. Preserve the existing Jev model, rubric, match/filter/qualification/seniority outputs, and current budget behavior. Jev remains the sole authority for candidate/job matching.
2. Run applicable deterministic hard gates and Jev assessment before generation. Pass the persisted Jev result to the GPT agent as read-only, versioned context. A Jev conflict blocks draft generation; review or unassessed results require owner resolution. GPT may flag a possible mismatch but cannot calculate, rank, write, or override Jev decisions. Re-run Jev only when its inputs or rubric materially change.
3. Use the [OpenAI Responses API](https://developers.openai.com/api/reference/resources/responses/methods/create) with model ID `gpt-6-luna` and `reasoning.effort: "max"`. [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs) define artifact schemas. Function calls are proposals; the local harness executes only explicitly allowlisted tools after checking arguments, scope, URLs, consent, and budget.
4. Put all external research in a distinct Researcher stage using the existing Scrapling-backed Clue crawler. The Researcher receives job/company search context but no CV, profile, or private claim data, and returns sourced facts, excerpts, timestamps, uncertainty, and contact evidence where enabled. The later writing/practice stages receive that cited packet and have no crawl or general network tools. Do not give any model stage arbitrary filesystem, database, shell, or logged-in browser access.
5. Send only the selected CV and role-relevant content needed for tailoring, the read-only Jev result, reviewed claim evidence, and confirmed writing preferences. The selected CV/profile content is personal data; require separate OpenAI opt-in. Keep other CVs, raw writing samples, and irrelevant profile details local. Preserve originals; local rendering creates versioned copies and applies the selected structure unless the owner opts into improvements.
6. Do not expose Gmail, message-send, connection-request, employer-form, or application-submit tools to GPT. After the owner reviews and approves the exact outreach recipient, subject, and body, a separate UI-triggered Gmail adapter may create an unsent draft; the owner sends it manually. Clue needs its own Google OAuth or connector authorization; the Gmail connector available in Codex does not transfer to the API agent. Gmail's `gmail.compose` scope supports draft management and sending, so the adapter must isolate the credential and expose draft creation only. If the owner requires a credential without send capability, use a Clue-local or `.eml`/copy-to-Gmail handoff instead.
7. Keep local rendering deterministic and versioned. The agent cannot overwrite source CVs. Reject stale inputs and unapproved claim references; show the owner the complete final output, sources, unresolved questions, and changes. Schema compliance does not establish semantic truth.
8. Preserve Jev's existing $4 rolling 30-day app reserve toward the $5 owner ceiling. Maintain a separate OpenAI usage ledger, monthly cap, and per-opportunity cap. The owner has not set the OpenAI cap amount; API calls remain disabled until both caps and separate OpenAI data-sharing consent are configured. Never silently downgrade effort or switch providers when blocked.
9. Treat current OpenAI prices as volatile. The official [GPT-6 Luna model page](https://developers.openai.com/api/docs/models/gpt-6-luna) listed $0.10 per 1M input tokens and $0.50 per 1M output tokens on 2026-10-06; tool charges may be additional. Recheck pricing, account controls, terms, and data handling immediately before enabling provider calls. These prices are planning evidence, not permanent constants.
10. Keep application forms and submissions manual and outside Clue. A packet never marks an opportunity as applied; the existing applied tracker remains authoritative. Clue may record a later owner attestation or receipt. Do not provide a send or submit function.
11. Keep claims, CVs, opportunities, packets, contact research, consent, and usage records local. Do not commit personal source documents, claim values, contacts, answers, or generated packets to the public repository.
12. Orchestrate distinct GPT-6 Luna (`reasoning.effort=max`) stages with strict schemas: Diagnoser audits locally extracted resume text/layout for observable readability risks; Recruiter maps job criteria to owner-reviewed claim IDs and reports document-evidence coverage while displaying Jev read-only; Rewriter proposes evidence-bound bullet patches using Google's X/Y/Z accomplishment pattern; Hiring Manager optionally runs role-specific interview practice and scores only the owner's answers against a transparent practice rubric. The Recruiter must not create a competing candidate-fit score. The Diagnoser must not claim to simulate an unknown employer ATS or explain ghosting. The Rewriter must not invent or estimate metrics, and metrics are not required in every bullet. The Hiring Manager's ratings are not Jev results, hiring predictions, or employer scores. These roles use the same configured GPT-6 Luna model as separate orchestrated calls; they do not hold independent credentials or tools. Jev remains the only matching validator and may inform practice topics from its read-only gaps, but it does not score ATS parseability, prose, bullets, or interview answers.
13. Keep preparation opt-in per listing. Normal discovery, identity deduplication, deterministic hard gates, Jev matching, and ranking may run automatically as they do in the search workflow, but they must never start Researcher or GPT writing/practice calls. Only the owner clicking **Prepare application** on a specific eligible `match` listing creates a preparation request for that opportunity. No bulk-selection, recurring job, or background queue may create triggers. Bind the click to the job snapshot, Jev run, and relevant profile/CV/claim/policy revisions; reserve OpenAI budget only after the click; make repeated clicks idempotent. The click runs the complete research and document packet for that listing. Mock interview practice is a separate optional owner-triggered action. Final review, Gmail draft creation, and manual send/application submission retain their existing boundaries.

## Consequences

- Core M0–M5 local workflow code is implemented. The app adds evidence review, a per-listing preparation queue, bounded research/generation, versioned artifacts, exact packet approval, owner-reported outcomes, and an isolated Gmail draft adapter.
- Jev continues to own matching; the GPT agent is a bounded research and content worker. Its results cannot change match eligibility.
- OpenAI API work requires a non-empty key, separately configured monthly and per-opportunity caps, a current rate card, and explicit data-sharing opt-in because personal profile-derived content may leave the device. The OpenAI key is intentionally blank in `.env.example`; a key alone will not enable calls. Provider terms and data controls must be reviewed before activation.
- A local usage reservation and settlement ledger must account for input/output usage and applicable tool charges. Timeouts with uncertain usage retain the reservation until reconciled.
- New private records use additive SQLite schema creation and are included in search-reset retention and full personal-data deletion. Synthetic tests cover the new data cleanup paths.
- Candidate evidence is reviewed during initial local source onboarding; after that setup, each opportunity has one final packet review. The owner may then ask the separate adapter to create an unsent Gmail draft, but must send it themselves; application forms and submissions stay manual.
- Search and Jev matching may operate automatically; GPT research and preparation begin only from a deliberate per-listing owner action. Unrequested listings consume no OpenAI or contact-crawl budget.
- Gmail draft creation requires a scope that also permits sending. The model has no Gmail tool, and the adapter must omit send operations. A local email handoff is the fallback when that credential scope is not acceptable.
- GPT-6 Luna max is the configured stage effort requested by the owner. The local ledger records stage-level tokens, tool use, and estimated/settled cost. A real owner-rated writing pilot, latency review, and current price/account verification remain pending until the owner configures the provider after development.
- The optional background worker, automated follow-up reminders, external tracker synchronization, and cohort analytics are deferred. They require measured usage or a separate owner decision and are not prerequisites for the manual-trigger workflow.

## Validation evidence

The design direction was owner-approved on 2026-10-06. Synthetic validation recorded for the current local implementation: 22 application-preparation tests pass; Ruff and byte-compilation pass. No live OpenAI call, Gmail action, real CV/profile use, or employer submission was performed. The repository-wide test suite remains non-green: with the Scrapling-dependent test excluded, the current checkout has 142 passes and 38 failures; the unmodified `HEAD` archive has 134 passes and 38 failures. Existing environment/dependency and test-expectation issues remain open, so full-suite validation is not claimed. `.env.example` keeps the key blank by request.
